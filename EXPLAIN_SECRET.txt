================================================================================
 LES SECRETS DU PROJET — EN BREF
================================================================================

POURQUOI 4 VALEURS
  MySQL cree sa base et son compte au 1er demarrage avec :
    mysql_root_password   mot de passe admin de la base
    mysql_database        nom de la base        (wordpress)
    mysql_user            compte applicatif     (wp_user)
    mysql_password        mot de passe de ce compte
  WordPress utilise les 2 derniers pour se connecter a la base.
  Sans elles, les conteneurs demarrent puis crashent en boucle.


LE CHEMIN DES VALEURS

  group_vars (chiffre, sur MA machine)
        |  Ansible dechiffre en memoire au deploiement
        v
  env.j2  --rendu Jinja-->  /opt/wordpress/.env  (sur le serveur, mode 0600)
        |  Docker Compose lit ce .env au lancement
        v
  ${MYSQL_PASSWORD}  -->  variable d'environnement du conteneur mysql

  DEUX moteurs differents :
    {{ mysql_password }}  = Jinja/Ansible, sur ma machine, au deploiement
    ${MYSQL_PASSWORD}     = Docker Compose, sur le serveur, au lancement


OU SONT LES VALEURS

  group_vars/*.yml (chiffre)        les vraies valeurs      committable chiffre
  roles/app/templates/env.j2        {{ mysql_password }}    versionne, sans risque
  /opt/wordpress/.env (serveur)     valeurs en clair, 0600  jamais dans git

  JAMAIS de valeur en clair dans un .j2, dans le playbook, ou dans un fichier
  versionne : le sujet l'interdit explicitement.


GENERER UN MOT DE PASSE

  openssl rand -base64 24

    openssl      boite a outils cryptographique
    rand         genere des octets aleatoires (source du systeme, /dev/urandom)
    24           24 octets = 192 bits d'entropie (incassable en force brute)
    -base64      encode ces octets en caracteres imprimables (A-Z a-z 0-9 + / =)
                 -> sortie de 32 caracteres, collable dans un fichier texte

  A lancer une fois par mot de passe. Ne jamais le coller ailleurs que dans le
  fichier de secrets : un mot de passe passe par un chat / un mail est a
  considerer comme compromis, on le regenere.


METHODE 1 — FICHIER DE SECRETS CHIFFRE (celle du projet)

  cp group_vars/webservers.yml.example group_vars/webservers.yml
  nano group_vars/webservers.yml
  ansible-vault encrypt group_vars/webservers.yml

  head -1 group_vars/webservers.yml     # doit afficher $ANSIBLE_VAULT;1.1;AES256

  Le fichier entier est chiffre en AES256. all.yml reste lisible pour les
  variables non sensibles (project_dir, ports...).


METHODE 2 — VALEURS CHIFFREES DIRECTEMENT DANS all.yml

  Si on veut tout regrouper dans group_vars/all.yml, on chiffre chaque valeur
  une par une :

  ansible-vault encrypt_string 'MON_MOT_DE_PASSE' --name 'mysql_root_password'

  La commande affiche un bloc a coller tel quel dans all.yml :

    mysql_root_password: !vault |
              $ANSIBLE_VAULT;1.1;AES256
              66383439383...

  Ansible dechiffre la valeur au moment de l'utiliser. all.yml reste lisible,
  les secrets restent illisibles, et le fichier est committable.


UTILISATION

  ansible-playbook playbook.yml --ask-vault-pass    # demande le mot de passe
  ansible-vault view group_vars/webservers.yml      # relire les valeurs
  ansible-vault edit group_vars/webservers.yml      # modifier sans dechiffrer sur disque

  Le mot de passe du vault n'est stocke nulle part : il est irrecuperable.


POURQUOI PAS SEULEMENT .gitignore

  .gitignore empeche la publication, mais le fichier reste en clair sur le
  disque. Le vault chiffre au repos : vole, il reste inexploitable.


SUR LE SERVEUR

  /opt/wordpress/.env est en 0600 (root uniquement).
  MySQL n'expose aucun port vers Internet, seul le reseau Docker interne y
  accede. Les valeurs en clair ne sont donc lisibles que par quelqu'un qui est
  deja root sur la machine.
